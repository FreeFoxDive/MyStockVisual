# K 线切换延迟分支：评估与修改方案

审查日期：2026-09-15。目标分支：`perf/kline-switch-latency`，提交 `1ba3723`。
审查时主仓库 `visual/` 与该分支的 tree 一致。本文保留初审结论与方案；修复结果见文末。

## 结论

优化方向合理：提高历史日 K 缓存命中率、移走 ETF 慢派生字段、复用短期快照、减少 Python 和浏览器 CPU 开销，都对应实际主路径成本。

当前实现不宜直接合并。主要问题不在指标公式，而在后台任务生命周期、熔断资源边界和异步溢价刷新闭环。优先修复这些问题，保留现有优化，不需要重写行情系统。

不能将以下几项等同：单源等待 8 秒不等于整请求 8 秒；浏览器 abort 不等于取消 Flask 执行；NAV 日频不等于溢价日频；缓存存活 1.25 秒不等于交易所行情绝对延迟小于 1.25 秒。

## 六项优化的合理性与正确性

### 1. 日 K 磁盘 TTL：盘中 300 秒、盘后 1800 秒

- 建议保留。减少历史序列重复取数有实际价值；分钟 K 的 TTL 没有被一起放大。
- 交易日日 K 跳过响应级内存缓存；磁盘命中后仍移除当日 bar，并尝试以快照重新拼接。主要 OHLCV 契约保持。
- 这不会消除所有冷请求，只减少重复请求走上游的频率。收益依赖真实访问间隔和命中率。
- 边界：除权后的历史修订在 TTL 内可能未生效；快照不可用时，磁盘命中路径可能缺当日 bar。这些机制原本存在，增大 TTL 会扩大部分窗口。
- 建议为磁盘缓存补充生成交易日期，跨日失效，防止午夜前写入的“已剥离当日 bar”缓存在午夜后继续遗漏上一日。不要用“末根必须是上一交易日”简单判失效，停牌标的可能合法缺 bar。

### 2. 单源等待超时与源级熔断

- 必须有等待预算，方向正确；现实现只能限制调用者等待时间，不能终止后台线程。
- 已确认 P1：全部源冷却时，每个请求都破例调用链首；冷却到期后也会继续创建新线程。没有资源硬上限。模拟阈值 1、连续 5 个请求，源仍在冷却而存活线程已有 5 个。
- 同一个源名称还覆盖多种接口。空数据、标的不支持或分钟数据陈旧不一定代表整个供应商故障，容易扩大熔断影响。
- 多源串行、复权回退、报价与名称/元信息访问不全在这 8 秒内。现阶段不能承诺端到端超时。

### 3. ETF 溢价后台化

- 应保留异步拆分。净值查询不应阻塞 OHLCV 和指标返回；按 date 回填也比依赖数组位置稳健。
- 当前未完成刷新闭环：前端最后一次查询约在第 6 秒；后台第 7 秒完成就无法自动显示。日/周/月 K 的 tail 更新不重新拉溢价。
- 前端内存溢价没有有效期，即使手动刷新行情也可能一直复用旧值。
- 后台单飞只有同 key 防重，没有超时和全局并发上限。NAV 永久挂起会永久占据该 key，切换不同标的仍会新建线程。仅延长前端轮询解决不了此问题。
- 30 分钟/6 小时缓存的是最终溢价，而溢价还依赖价格。历史值与当前末根应分别考虑；至少应公开计算时间，不能将缓存值称为实时溢价。
- 模块注释称 stale-while-revalidate，但当前过期结果不返回，只返回 ready=false。应落实该语义或更正注释。

### 4. 图表复用 1.25 秒快照

- 建议保留。属于明确、可回退的新鲜度取舍；OHLCV 仍由后端生成，前端不自行派生。
- 已有测试覆盖盘前、非交易日、停牌零成交量、陈旧日期、高低缺失，以及覆盖滞后源 bar。
- 本分支保持 `get_daily_bar` 和默认调用方 `fresh=True`，未发现由本次修改引入的成交校验放宽。
- 但既有 `fetch_quotes` 在锁竞争时会返回缓存，取数失败也可能回退缓存。因此准确说法是“成交校验保持原有强刷策略”，不是“所有并发/故障场景都保证本次网络新取”。若要升级该契约，应另行实现并测试。

### 5. 按列序列化

- 建议保留，风险低，实际减少了每行创建 Series 的开销；指标计算公式未变。
- 本地 1006 根合成样本、7 次中位数：完整指标旧实现 88.23ms，新实现 39.92ms；字段值和 JSON 字节一致。旧实现从目标分支父提交提取。
- 缺列样本：86.90ms → 35.26ms，字段值一致，但缺失字段被追加到末尾，JSON 字节不一致。这不影响正常按字段访问的前端，但“全部输入字节一致”表述不成立。
- 当前测试的部分基准复用了重构后的 helper，字段顺序断言甚至是同一列表与自身比较。需要独立基线验证。

### 6. 前端取消请求与 localStorage 优化

- 保留 AbortController 和响应版本检查，能减少浏览器接收、解析废弃响应及错误提示。
- 当前 Waitress 同步调用 Flask，路由没有协作取消检查。abort 不会自动释放已经执行的服务端工作线程；不能把它计为服务端任务取消方案。
- 当前优化只移除了 localStorage 淘汰扫描时的整包 JSON.parse；读取选中标的缓存仍有整包 parse，getItem、JSON.stringify、setItem 仍同步执行。收益应按实际减少的操作描述。
- 时间戳前缀解析有安全降级，未发现本次修改造成淘汰策略的功能回归。

## 具体修改方案

### A. 优先修复取数资源边界

修改 `kline_source.py`，测试落在 `test/test_kline_source.py`。

1. 增加每源并发上限和全局上限，例如先以每源 2、全局 6 为可配置起点，实际值由压测决定。限额非阻塞获取，满额直接跳过，不建立无界排队。
2. 配额必须在工作线程真实退出的 finally 中释放，不能在调用方 join 超时后释放。这样永久挂起时资源仍有硬上限。
3. 删除“所有源冷却就无条件重试链首”。采用 closed → open → half-open 状态；冷却到期后原子地只放行一个恢复探测，而且仍受并发上限约束。
4. 成功关闭熔断、失败重新冷却；状态使用 monotonic 时钟。避免旧请求的迟到结果覆盖新一轮熔断状态。
5. 所有源不可用时返回现有无数据/获取失败结果，记录明确原因。没有可用数据时，不能为了避免失败响应而重新制造无限工作。
6. 对供应商适配器逐步区分 timeout/transport/rate-limit 与 no-data/unsupported/stale；前者才适合触发供应商级熔断。首轮至少不要把明确 unsupported 和本地容量不足计作源故障。
7. SDK 支持的地方配置连接/读取超时。无法取消的调用维持有界隔离；若必须自动回收永久挂起任务，使用可终止子进程，不能声称 Python daemon 线程可强杀。

验收：挂起源持续被访问、多个请求并发、全部源冷却、冷却到期恢复、旧请求迟到五种场景下，线程数不超过配置上限；半开探测仅一个，正常回退仍可成功。

### B. 补齐溢价 provider 生命周期与协议

修改 `premium.py`、`market.py` 和 `api/kline.py`，测试落在 `test/test_premium.py` 及 API 测试。

1. 给 premium 工作加全局容量上限，NAV 在 symbol 级共享单飞，避免不同 period/count 同时重复抓同一净值。超时后也不能提前释放实际仍占用的工作槽。
2. 在现有 `ready/dates/values/params` 上增量增加 `status`、`stale`、`generated_at`、`max_age_sec`、`retry_after_sec` 和覆盖日期。保留旧字段便于兼容。
3. 区分 pending、ready、暂时失败和无数据。失败按负缓存截止时间重试，永久缺数据停止忙轮询，错误只返回固定分类。
4. 缓存过期可返回带 stale 标记的历史结果并后台更新；新鲜度不明时不要将旧值伪装为新结果。失败状态同样应能携带最后一次成功的历史结果。
5. 缓存携带生成交易日期和覆盖日期；跨日与新 bar 触发更新，避免长 TTL 阻止新日期出现。
6. 保留历史溢价的长缓存，但当前末根应独立刷新。优先在后台按较短可配置周期更新未复权 close，并与缓存 NAV 计算；返回价格/NAV 对应日期和计算时间。不要把前复权图表 close 直接用于溢价。
7. 若需要盘中实时溢价，再将最新未复权快照接入后端末根计算，明确与旧版历史 raw close 的口径差异，独立验证；不应偷偷夹在性能优化中改变公式。

验收：10 秒后完成仍能取到；失败后按负缓存恢复；永久挂起资源有界；同 symbol 多周期只抓一次 NAV；跨日覆盖新增日期；旧历史结果可标记为 stale 返回；前复权/后复权切换不改变 raw-close 溢价口径。

### C. 前端补齐查询、过期与取消

修改 `static/index.html`，以真实函数运行测试替换仅源码字符串检查。

1. 每个视图维护递增 requestId，包含 symbol、period、count、adjust；不单用 Date.now 充当请求唯一标识。
2. premium 独立管理 AbortController 和重试 timer，换股/切周期立即取消。检查版本时同时核对当前视图，迟到结果不回填。
3. pending 时先短退避，随后固定低频查询，例如间隔上限 10 秒；按服务端 retry_after 调度。视图切走或页面隐藏时暂停，恢复可见后按过期状态继续。
4. 内存结果保存 fetchedAt、有效期、count 和覆盖日期；可先回填有效历史数据，但不能因为有 map 就永久 return。数据过期、手动刷新、tail 新增日期时均检查是否需要更新。
5. 对同一 key 的补齐请求保持前端单飞，防止手动刷新与定时任务叠加。
6. loading 收尾与前台请求 ID 绑定；silent 刷新不得让前台 loading 永久残留，也不得取消前台请求。K 线与 premium 各自持有控制器。
7. 更正 abort 的注释：取消浏览器请求，不承诺终止服务端。服务端负载由 A/B 的有界任务保证。

验收：后台第 7/15/30 秒完成；同标的跨有效期刷新；新增交易日；A→B→A 快切；同毫秒请求；切周期、复权、隐藏/恢复；前台与 silent 请求交错。验证请求次数、DOM/数据结果与取消行为，不以“源码包含某字符串”为通过标准。

### D. 小范围巩固缓存与序列化契约

1. 保留 300/1800 秒配置，增加跨生成日期失效测试；覆盖盘中→午休→收盘、快照失败与除权历史修订窗口。
2. `serialize_bars` 按 `_BAR_FIELDS` 的原顺序写入所有字段，缺列在原位置写 None；仍按列提取数据。若决定不保证字节顺序，则修改文档并以字段等价作为契约。
3. 测试使用冻结的旧版序列化实现或独立 golden payload；同时验证完整指标、缺列、NaN、日期格式与实际 JSON 输出。
4. 保留 localStorage 淘汰前缀读取，补畸形/旧格式条目降级测试即可，暂不扩大到存储架构重写。

## 验证与合并顺序

1. 先完成 A 和 B/C 的生命周期修复；这些是合并阻断项。
2. 完成 D 和注释修正，运行本分支相关测试及新增行为测试。上一轮相关 139 项测试通过；这并不覆盖上述已复现问题。
3. 离线性能验证分开测：Python 序列化、历史磁盘命中、快照命中、premium 未就绪返回。使用固定输入和旧分支对照，不访问真实交易接口。
4. 真实环境验收再测冷/热缓存、股票/ETF、日/周/月/分钟、快速连续换股，记录首图可见时间和溢价就绪时间的 p50/p95，同时记录源调用数、超时数、活跃工作数。
5. `total_ms` 当前不足以代表浏览器端到端延迟；补充或单独测 JSON 编码、缓存读写、DOM/ECharts 绘制。不要将局部 88→40ms 外推为整页提速比例。

本次已验证：代码路径、既有相关测试、挂起线程增长复现、延迟溢价遗漏复现、内存结果永不过期复现、旧版与新版序列化对照。未做真实供应商故障压测，也未测生产网络端到端 p95。

## 实施结果（2026-09-15）

- 已实现每源 2 / 全局 6 个 K 线实际工作槽、冷却后单个探测和状态代际校验；容量不足不增加源失败计数。已有 AlphaFeed/Mairui 客户端本身配置了网络超时，继续保留。
- premium 默认最多 4 个后台工作，30 秒后对外报告失败但不提前释放真实工作槽；NAV 同 symbol 单飞。过期结果带 stale、计算日期/时间、剩余有效期和建议重试间隔返回。
- NAV 继续长缓存，最终溢价盘中每 60 秒可刷新。采用复用 NAV 后重新向量化整段溢价的简单实现，避免引入历史/末根两个不同版本的结果；仍使用原有未复权历史 close 公式，没有改为实时 IOPV。
- 前端支持持续退避、负缓存等待、视图取消、15 秒 HTTP 请求等待上限、隐藏暂停/可见恢复、有效期与日期覆盖检查；手动刷新重新查询。过期徽标显示“待更新”和计算时间。
- 请求版本改为递增序号；前台加载期间跳过 silent 刷新，旧请求不清除新请求 loading。补充交易记录异步返回后的版本检查。
- 日 K 磁盘缓存按北京时间生成日期跨日失效，兼容旧格式；缺列序列化也保持 JSON 字段顺序，测试使用独立冻结的字段基线。
- 开盘、午休、收盘时段变化也使溢价缓存失效；客户端最多 60 秒重新确认，防止盘前长 TTL 延续到盘中。
- 新增 19 项行为回归；修复旧成交测试依赖真实运行时段的问题，明确固定在收盘后场景，生产盘前守卫未改。
- Visual 全量：`python -m unittest discover -s test`，912 项，910 通过、2 跳过，无失败。所有内联脚本语法检查通过；1006 根完整指标序列化复测约 81ms → 39ms。

资源界限按单个服务进程计。不可取消的第三方调用若永久挂起，会一直占用有限工作槽；本次保证有界降级，不声称能终止 Python 线程。供应商更细的故障分类、可终止进程隔离、真实网络 p95 验收仍属于后续增强。
